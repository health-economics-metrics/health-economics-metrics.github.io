# SPACE與開發者體驗（DevEx）

SPACE（滿意度與幸福感、績效、活動量、溝通與協作、效率與流動）與DevEx（反饋迴圈、認知負荷、心流狀態）是用於**多維度**衡量開發者生產力的框架——這是該領域對"沒有任何單一指標能經受住現實檢驗"這一發現的回應。

## 為何重要

這兩套框架都體現了健康結果研究早在數十年前就艱難習得的同一條教訓：單一數位（程式碼行數、血壓）無法真實反映多維度的現實，而對其進行最佳化只會催生操縱行為，而非真正的改進。SPACE要求至少組合三個維度的指標，同時混合遙測資料與自我報告——這在結構上與[EQ-5D](../EQ-5D/)在計算任何指數之前先對五個維度分別刻畫完全相同，也正是[PROM](../病患報告結果/)之所以與臨床測量並存的原因。滿意度/幸福感同樣絕非軟性點綴——它直接影響[人才留任](../人才留任/)經濟學，而人才流失的代價正是以負荷薪資的月數來定價的。

## 計算方法

這兩套框架都不是公式，而是測量設計：

```
SPACE原則：至少涵蓋3個維度，至少1項感知類（調查）指標 + 至少1項系統類（遙測）指標

DevEx各維度及示例配對：
  反饋迴圈   → CI耗時（遙測）+ "等待感覺很慢"（調查）
  認知負荷   → 檔案可查詢性、入職耗時 + 主觀感受的費力程度
  心流狀態   → 會議/打斷密度 + 自我報告的專注度

衍生指數（例如DX公司的DXI）將調查複合指標對映為時間：
供應商主張約為每個指數點相當於每名開發者每週13分鐘——
應將其視為一個需要在本地驗證的供應商基準，而非一條自然常數。
```

## 實例演算

某平臺團隊為300名開發者論證一項DevEx投資（CI提速+檔案改造）的合理性：

```
基線：CI耗時p75 = 28分鐘；調查"我在等待建置時會失去專注"：62%表示同意
改進後：CI耗時p75 = 9分鐘；同意比例降至24%

回收的時間（遙測資料）：每天6次建置 × 19分鐘 × 0.4可用係數 = 每名開發者每天約45分鐘
產能價值：300 × 0.75小時 × 220天 × £60/小時 ≈ 每年£297萬（非現金釋放型——
參見cash-releasing-vs-non-cash-releasing.md；這裡的0.4可用性係數，正是
practitioner-time.md中所述的碎片化折扣）
感知層面的印證，正是讓遙測資料主張變得可信的關鍵——單獨使用其中任何
一種都容易被操縱；二者結合，才能形成相互印證的三角驗證。
```

## 與軟體工程的聯絡

這份檔案本身*就屬於*軟體的一側；而真正值得指出的遷移方向，反倒是流向健康經濟學。一個"品質調整工程師年"——按標準化體驗指數加權的時間——正是[QALY](../品質調整生命年/)的構造方式應用到工程產能上的體現，它也繼承了QALY的規則：權重必須來自經過驗證的量表工具（一致的調查、已公佈的計分方法），並且必須在比較*之前*就先行確定，絕不能事後調整以美化某個偏好的工具。[SF-6D與EQ-5D](../EQ-5D/)之間的教訓同樣適用：不同的量表工具會系統性地給出不同的數位，因此絕不應跨越不同供應商的量表工具去比較DevEx指數。

## 陷阱

- **壓縮為單一指標**：把SPACE壓縮成一個單一分數的儀表盤，恰恰重新制造了這套框架本想防止的問題。
- **將活動量指標當作結果**：提交次數、PR數量與故事點，都屬於"活動量"維度——而SPACE明確警示，這正是最容易被操縱的維度（健康領域的對應類比：統計做了多少次手術，而非統計康復了多少人）。
- **調查疲勞與霍桑效應**：輕量級的季度調查工具，效果優於每週一次的高強度問詢。
- **團隊之間的比較**：就像未經病例組合調整的醫院排行榜一樣——領域差異、歷史遺留負擔、待命值班等情境差異，往往起著主導作用。
