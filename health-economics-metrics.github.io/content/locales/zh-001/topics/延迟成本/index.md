# 延迟成本（CoD）

延迟成本是指某项功能、产品或服务在*未*交付期间，每单位时间所损失的经济价值。它是软件交付指标与健康经济学之间最强有力的桥梁：能将"我们交付晚了"这句话，转化为货币价值——或转化为QALY。

## 为何重要

Reinertsen法则："如果你只量化一件事，那就量化延迟成本。"大多数组织知道一个项目要花多少钱，却不知道延迟一个月要付出什么代价，于是它们在优化预算的同时，正持续流失着时间价值。对医疗软件而言，赌注是真真切切的：一项路径改进每延迟一周，患者就要在更差的健康状态下多等一周。延迟成本是向NHS利益相关方展示时最有力的数学框架，因为它为你软件的"缺席"本身定了价。

## 计算方法

```
延迟成本 = 未交付期间、每单位时间所放弃的效益   （£/周 或 QALY/周）

总延迟损失 = 延迟成本 × 延迟时长

关于优先级排序，参见wsjf-and-cd3.md：CD3 = 延迟成本 / 时长。
```

对于临床软件，应同时以健康与货币两种单位计价：

```
延迟成本_健康 = 每周受影响患者数 × 每名患者的QALY获益
延迟成本_货币 = 延迟成本_健康 × λ (支付意愿阈值，£20,000–30,000/QALY)
              + 每周被放弃的运营节省
```

## 实例演算

**运营场景**：某软件在一条诊疗路径上为每名患者节省£200；某信托机构每周处理50名此类患者。

```
延迟成本 = 200 × 50 = 每周£10,000
一次10周的采购延迟，会造成 200 × 50 × 10 = £100,000 的可避免浪费。
```

**临床场景**：某项分诊改进使每周100名患者的等待时间缩短5周（效用值从0.68提前提升到0.80）：

```
每名患者的QALY获益 = (5/52) × 0.12 ≈ 0.0115
延迟成本_健康 = 100 × 0.0115 = 每周1.15 QALY
延迟成本_货币 = 1.15 × £20,000 ≈ 每周£23,000的健康价值
```

一次6个月的部署延迟，其"代价"约为30个QALY——这一论证能将一次IT系统上线延期，重新定性为一起临床事件。（作为规模参照：Black Swan Farming著名的马士基案例研究发现，单个功能的延迟成本可高达约每周$200,000，且该功能已等待了38周。）

## 与软件工程的联系

延迟成本是能让[DORA前置时间](../DORA指标/)与[流动效率](../流动指标/)在财务上变得可读的指标：前置时间 × 延迟成本 = 在队列中被白白烧掉的金钱（或健康）。其用途包括：

- **优先级排序**：按延迟成本/时长（参见[WSJF/CD3](../WSJF与CD3/)）对工作进行排序，而非按谁的嗓门最大来排序。
- **流程经济学**：与持续交付相比，一个2周的发布节奏预期会带来约1周 × 每个功能的延迟成本这样的额外延迟成本——为这种"批量交付"定价。
- **采购**：NHS长达6–18个月的采购周期本身就有延迟成本；把这一点展示出来，能改变关于紧迫性的对话（可负担性方面的对应概念，参见[预算影响分析](../预算影响分析/)）。

## 陷阱

- **假设延迟成本是线性的**：有些工作的价值呈"截止日期"形态（监管日期——过期后延迟成本趋于无穷大，之前则为零），有些则呈递减形态（先发优势窗口）。在相乘之前，应先判断其紧迫性剖面属于哪一种。
- **对无人想要的产出计算延迟成本**：只有当事物本身具有价值时，延迟才会产生代价；延迟交付一堆垃圾，代价为零。
- **重复计算延迟成本与贴现**：[贴现](../贴现与时间偏好/)本身已经为跨越多年时间范围的时间因素定了价；延迟成本是同一时间范围*内*、运营层面的版本。应在按周/月计算时使用延迟成本，在按年计算时使用净现值调整。
