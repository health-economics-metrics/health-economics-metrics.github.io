# 限界費用と平均費用

平均費用とは、総費用を生産単位数で割ったものです。限界費用とは、*追加*で1単位を生産するための費用です。意思決定は限界費用に基づいて行うべきですが、公表されている単位費用はほとんど常に平均費用です。

## なぜ重要か

デジタルヘルスのビジネスケースにおける最も一般的な誤りは、節約されたリソースを**平均**費用で評価することです。実際の節約は**限界**費用であるにもかかわらずです。病院の病床1日あたりの平均費用(全額配賦)は£400以上ですが、病床を1日分空けても£400は節約されません — 建物、暖房、そしてほとんどの人件費は変わらず発生し続けます。実際に解放される現金は、病棟を閉鎖できるだけの病床が空かない限り、£50〜£150程度にすぎません。

## 数式

```
平均費用: AC = TC / Q
限界費用: MC = dTC/dQ   (1単位多い/少ない場合の費用)

TC = 総費用、Q = 数量
```

固定費のため、容量削減時にはMC < ACとなり、余剰容量がある場合はMCはゼロに近づくことがあります。節約の主張には以下を使うべきです:

```
真の節約 = ΔQ × MC          (小さな変化の場合)
真の節約 = TCの段階的変化    (容量の閾値を超える大きな変化の場合、例:病棟の閉鎖)
```

## 計算例

あなたのソフトウェアが平均在院日数を短縮し、あるトラストで年間1,000病床日を空けたとします。

- **素朴な主張**:1,000 × £400(平均費用)= **£400,000節約**。誤りです。
- **限界費用に基づく主張**:病床1日あたりの変動費(食事、洗濯、消耗品、一部の看護人員の融通)≈ £120。節約 = 1,000 × £120 = **£120,000**、*加えて*、空いた病床が待機中の選択的手術患者で埋まる場合はその容量の価値(出来高払い制度下での収入、あるいは待機リストの削減)。
- **段階的変化の主張**:トラストが年間7,300病床日を空ける(20床の病棟に相当)場合、実際にその病棟を閉鎖できます:人件費+運営費 ≈ 年間£150万の実際の現金。この場合、平均費用の計算は真の値に近づきます。

同じ介入でも、変化が容量の段階を超えるかどうかによって、3つの弁護可能な数値が生じます。

## ソフトウェア工学との関連

クラウドの経済学はまさに限界費用の領域です:

- すでに予約済みの容量上で追加のCI実行を1回行う限界費用は≈£0ですが、実行1回あたりの平均費用(プラットフォーム全体の支出÷実行回数)は数ポンドになることがあります。平均費用を課金する内部課金制度は、実際には限界的に無料である共有容量をチームに過小利用させます。
- 逆に、「コンピューティングの30%を節約した」が現金を解放するのは、インスタンスが実際に停止されるか、予約が削減された場合に限られます — これは病床日の罠のソフトウェア版です。[現金化可能な節約と非現金化節約](../cash-releasing-vs-non-cash-releasing/)を参照してください。

## 落とし穴

- **容量を平均費用で評価し**、それを現金として提示すること(典型例)。
- **限界費用が一定だと仮定する。** 限界費用は容量の境界(病棟の閉鎖、ライセンスの段階、予約インスタンスの契約)で段階的に変化します。
- **同じケースの中で、拡大の意思決定には限界費用を、縮小には平均費用を使う**こと — 実際の意思決定に応じて選ぶべきです。
