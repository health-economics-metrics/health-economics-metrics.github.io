# 技術債務

技術債務是指程式碼庫中過去權宜之計的決策所暗含的未來成本：所欠下的補救工作（**本金**），以及它對交付所施加的持續拖累（**利息**）。SQALE一類的量化方法，能將其從一個比喻轉化為一項可核算成本的負債。

## 為何重要

未經量化的技術債務只是牢騷；經過量化，它就是一份商業案例。行業基準資料（CAST Appmarq，1,400個應用/5.5億行程式碼）：歷史上每行程式碼約承載**3.61美元**的技術債務本金，典型程式碼庫的債務比率通常為重建成本的15–20%，而常用的健康基準線為≤5%（SonarQube的"A"級）。健康經濟學的框架在此恰好契合：債務是一種*慢性病*——若不加處理，它會不斷進展，其"利息"以交付速度放緩與缺陷率上升的形式複利累積，而補救工作與新功能開發爭奪同一份產能，正如預防與治療爭奪同一份醫療資源一樣。

## 計算方法

```
SQALE本金       = Σ 所有違規項（補救所需時間）× 開發者成本費率
技術債務比率（TDR） = 補救成本 / 重新開發成本 × 100
                    （SonarQube評級：A ≤ 5%，B ≤ 10%，C ≤ 20%，D ≤ 50%）

利息（真正為償還投資提供論證依據的數位）：
  年利息 = Δ交付速度 × 每單位速度的價值
         + Δ缺陷率 × 每個缺陷的成本
償還論證 = 現值(時間範圍內被避免的利息總和) − 補救成本
          （需貼現——參見discounting-and-time-preference.md）
```

本金陳述的是負債本身；而**利息**才是這項投資論證的核心。花£500,000本金去避免每年£40,000的利息，是一筆糟糕的交易；若能避免每年£400,000的利息，則是一筆出色的交易。

## 實例演算

某40萬行程式碼的臨床記錄整合層：SQALE本金為3,800小時 × £75 = **£285,000**；TDR約為12%（C級）。實測利息：觸及該層的團隊，其週期時間比整體基線長40%，變更失敗率則是基線的2倍。該層每年吸收6,000個開發工時：

```
利息 ≈ 6,000 × 0.40 × £75      = 每年£180,000（速度拖累）
     + 12次額外故障 × £8,000    = 每年£96,000（返工/事件處理）
     ≈ 每年£276,000

針對熱點區域，償還本金中最嚴重的30%（£85,000）→ 建模顯示
利息可降低60%：每年節省約£166,000。回本週期約6個月。
```

熱點定位至關重要：債務利息往往集中在"變更頻率 × 債務密度"最高的地方——補救那些很少被觸及的債務毫無收益，就如同治療一種本來根本不會進展的病症（參見[預防經濟學](../預防經濟學/)）。

## 與軟體工程的聯絡

能提升技術債務論證水平的健康經濟學遷移要點包括：將整個資產組合表述為一份**負擔清單**（[DALY](../傷殘調整生命年/)式——健康工程年究竟損失在哪裡？）；誠實地以進展數學來論證償還的正當性（通常是具有成本效果，而非直接節省成本）；按[嚴重程度缺口](../QALY缺口與嚴重程度調整因子/)為最糟糕系統的補救工作加權；並在提交大型補救提案時，附上一份能經受住[規避的下游成本](../規避的下游成本/)規則檢驗的衝抵分析——機率加權、已貼現、只計算一次。

## 陷阱

- **只報告本金**：一個嚇人的大數位，若沒有配套的利息估算，說明不了任何問題。
- **將工具生成的債務數位奉為字面真理**：SQALE統計的是規則違反次數；它遺漏了架構層面的債務（往往才是代價最高的那種），卻計入了大量瑣碎問題。
- **零債務烏托邦主義**：最優的債務水平並非零——債務本質上是一種槓桿；真正的問題在於利率高低。
- **"重寫能一次性解決所有問題"**：重寫提案同樣必須經受住同一套衝抵規則的檢驗——反事實成本、機率、貼現，一樣都不能少。
