# 云单位经济学（FinOps）

云单位经济学将原始的云端支出，转化为**每单位产出的成本**——每客户、每笔交易、每例已处理案例、每个令牌。这正是FinOps的核心能力，它能把"我们的AWS账单是每月£400,000"这种说法，转化为"服务一名患者的成本是£0.83"。

## 为何重要

总支出数字无法回答那些真正重要的问题：产品的效率是在提升还是在下降？增长究竟是改善还是侵蚀了利润率？我们应该如何定价？单位成本可以同时回答这三个问题。就数字健康而言，"每例已处理案例的成本"本身*就是*一项医疗服务单位成本——可以直接与采购方用于所有其他服务的[全国成本采集](../全国统一收费标准与单位成本/)数据相比较，这使其成为将数字化路径与传统路径进行定价比较的天然语言。

## 计算方法

```
单位成本 = 已分摊的总成本（含共享/平台成本）/ 已交付单位数

两大类别：
  资源效率类单位：每GB存储成本、每vCPU小时成本、每令牌成本、
                 每构建分钟成本
  业务类单位：    每客户成本、每笔交易成本、每次问诊成本、
                 每例已处理案例成本

边际与平均的区分原则同样适用（参见marginal-vs-average-cost.md）：
已承诺/已预留的支出会使边际单位成本趋近于0，直到下一次
承诺阶梯为止——扩容决策应按边际成本定价，效率趋势判断
则应看平均成本。
```

## 实例演算

某数字化分诊服务：云端支出每月£62,000（计算£30,000，数据£18,000，共享平台分摊£14,000），每月处理380,000例分诊事件：

```
每例事件平均成本 = 62,000 / 380,000 ≈ £0.163

与采购方参照对比：电话分诊约£8–12/通，全科医生问诊约£42
→ 数字化事件的成本约为最便宜的人工替代方案的2%——这正是
  gds-service-metrics.md中渠道转移经济学在成本一侧的体现。

趋势检验：去年为每例£0.21，处理量为24万例 → 规模经济正在改善
（固定平台成本正被逐步摊薄），这一点值得在季度业务回顾中重点体现。
```

## 与软件工程的联系

单位经济学是工程决策转化为财务可读语言的地方：一种能将每例成本减半的架构，是一项定价优势；而一种呈超线性扩张成本的架构，则是一颗只有通过这项指标才能被察觉的定时炸弹。可从医疗成本核算中迁移过来的做法包括：**公开分摊规则**（共享成本曾一度扭曲单位成本数字，直到PLICS（病人层面信息与成本系统）实现了病人层面成本核算的标准化——你的平台成本分摊也需要同等的严谨性）；**选择采购方所熟悉的计量单位思考**（采购方购买的是"诊疗事件"，而非"vCPU"）；以及将单位成本作为权威的成本分母，输入到每一个[ICER](../增量成本效果比/)和[预算影响](../预算影响分析/)模型之中。对于AI功能而言，计量单位是令牌——参见[推理单位经济学](../推理单位经济学/)。

## 陷阱

- **忽视共享成本**：不含平台/安全/待命值班分摊的单位成本，通常会低估30–50%，一经审计便会站不住脚。
- **虚荣分母**："每次API调用成本"看起来很好看；"每例已完成患者诊疗事件成本"才真正有信息量。
- **对边际决策采用平均成本定价**：对边际上近乎免费的使用量向团队按平均单位成本收费，会催生形式主义的"节支表演"（NHS版本的这一激励机制缺陷，参见[全国统一收费标准](../全国统一收费标准与单位成本/)）。
