# 时间范围

时间范围是指一项分析中计算成本与效果所覆盖的期间。它必须足够长，才能捕捉到各备选方案之间所有有意义的差异。

## 为何重要

选择一个过短的时间范围，你会错过滞后出现的效益（预防）以及滞后出现的成本（维护）。选择一个过长的时间范围，一切又都会被不确定性所淹没。对于具有死亡率影响的治疗方案，卫生技术评估通常采用**终生**时间范围；而[预算影响分析](../预算影响分析/)则刻意采用较短的**1–5年**时间范围，因为它所关心的问题是可负担性，而非价值本身。时间范围是一项应当明确声明的建模选择，而不匹配的时间范围，正是操纵比较结果的经典手法之一。

## 计算方法

时间范围是任何评估中求和运算的上限：

```
净现值 = Σ (t = 0 … T) [ (效益_t − 成本_t) / (1 + r)^t ]

T = 时间范围（年）
r = 贴现率（参见discounting-and-time-preference.md）
```

报告结果时应明确说明所采用的时间范围，理想情况下应同时展示多个不同时间范围下的结果。

## 实例演算

某电子处方系统，实施成本£200万，每年运营成本£200,000。它每年可预防价值£600,000的用药错误（即被避免伤害所对应的治疗成本）。

按不同时间范围计算的净效益（为清晰起见，未贴现）：

```
时间范围1年：   −2,000,000 − 200,000 + 600,000  = −£1,600,000
时间范围3年：   −2,000,000 + 3 × 400,000        = −£800,000
时间范围5年：   −2,000,000 + 5 × 400,000        =  £0
时间范围10年：  −2,000,000 + 10 × 400,000       = +£2,000,000
```

该系统在任何低于5年的时间范围下都"失败"，而在10年时间范围下则"成功"。二者都不是真正的答案；诚实的报告应说明盈亏平衡点，并依据系统的实际使用寿命（多久后会被替换？）来论证所选时间范围的合理性。

## 与软件工程的联系

- **只在一个迭代周期内评估工具**，系统性地会错过学习曲线导致的效率下滑（成本前置）以及长期维护成本（成本后置）。在第2周就测量的AI编程助手试点，捕捉到的只是新鲜感高峰期，而非稳态表现。
- **合同期限 ≠ 效益时间范围。**如果你有合理理由预期会续约，即便是一份为期1年的SaaS合同，也可以按5年时间范围来评估——但必须说明这一点。
- **遗留系统替换类论证**，应覆盖旧系统可信的生命周期终点，而非一个随意选定的整数年份。

## 陷阱

- **时间范围购物**：挑选任何一个能让自己中意的方案胜出的时间范围。应在计算结果之前，就预先登记好所采用的时间范围。
- **在同一次比较中，对不同方案采用不同的时间范围**。
- **采用终生时间范围却不做贴现或不确定性分析**——按面值计算的第30年效益，不过是虚构的数字。长时间范围应搭配[敏感性分析](../敏感性分析/)一并使用。
