# 時間範圍

時間範圍是指一項分析中計算成本與效果所覆蓋的期間。它必須足夠長，才能捕捉到各備選方案之間所有有意義的差異。

## 為何重要

選擇一個過短的時間範圍，你會錯過滯後出現的效益（預防）以及滯後出現的成本（維護）。選擇一個過長的時間範圍，一切又都會被不確定性所淹沒。對於具有死亡率影響的治療方案，衛生技術評估通常採用**終生**時間範圍；而[預算影響分析](../預算影響分析/)則刻意採用較短的**1–5年**時間範圍，因為它所關心的問題是可負擔性，而非價值本身。時間範圍是一項應當明確宣告的建模選擇，而不匹配的時間範圍，正是操縱比較結果的經典手法之一。

## 計算方法

時間範圍是任何評估中求和運算的上限：

```
淨現值 = Σ (t = 0 … T) [ (效益_t − 成本_t) / (1 + r)^t ]

T = 時間範圍（年）
r = 貼現率（參見discounting-and-time-preference.md）
```

報告結果時應明確說明所採用的時間範圍，理想情況下應同時展示多個不同時間範圍下的結果。

## 實例演算

某電子處方系統，實施成本£200萬，每年營運成本£200,000。它每年可預防價值£600,000的用藥錯誤（即被避免傷害所對應的治療成本）。

按不同時間範圍計算的淨效益（為清晰起見，未貼現）：

```
時間範圍1年：   −2,000,000 − 200,000 + 600,000  = −£1,600,000
時間範圍3年：   −2,000,000 + 3 × 400,000        = −£800,000
時間範圍5年：   −2,000,000 + 5 × 400,000        =  £0
時間範圍10年：  −2,000,000 + 10 × 400,000       = +£2,000,000
```

該系統在任何低於5年的時間範圍下都"失敗"，而在10年時間範圍下則"成功"。二者都不是真正的答案；誠實的報告應說明盈虧平衡點，並依據系統的實際使用壽命（多久後會被替換？）來論證所選時間範圍的合理性。

## 與軟體工程的聯絡

- **只在一個迭代週期內評估工具**，系統性地會錯過學習曲線導致的效率下滑（成本前置）以及長期維護成本（成本後置）。在第2周就測量的AI程式設計助手試點，捕捉到的只是新鮮感高峰期，而非穩態表現。
- **合同期限 ≠ 效益時間範圍。**如果你有合理理由預期會續約，即便是一份為期1年的SaaS合同，也可以按5年時間範圍來評估——但必須說明這一點。
- **遺留系統替換類論證**，應覆蓋舊系統可信的生命週期終點，而非一個隨意選定的整數年份。

## 陷阱

- **時間範圍購物**：挑選任何一個能讓自己中意的方案勝出的時間範圍。應在計算結果之前，就預先登記好所採用的時間範圍。
- **在同一次比較中，對不同方案採用不同的時間範圍**。
- **採用終生時間範圍卻不做貼現或不確定性分析**——按面值計算的第30年效益，不過是虛構的數位。長時間範圍應搭配[敏感性分析](../敏感性分析/)一併使用。
