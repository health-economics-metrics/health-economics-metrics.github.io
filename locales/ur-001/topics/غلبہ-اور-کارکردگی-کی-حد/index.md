# غلبہ اور کارکردگی کی حد

ایک آپشن **غالب** ہوتا ہے اگر دوسرا آپشن کم لاگت رکھتا ہے *اور* زیادہ فراہم کرتا ہے۔ **کارکردگی کی حد** وہ ہے جو غالب آپشنز کو ختم کرنے کے بعد باقی رہتا ہے: انتخابات کا وہ مجموعہ جہاں زیادہ حاصل کرنے کے لیے زیادہ ادائیگی کرنی پڑتی ہے۔

## یہ کیوں اہم ہے

حدود یا بجٹ کے بارے میں کسی بھی بحث سے پہلے، صحت ٹیکنالوجی کی تشخیص پہلے ان آپشنز کو ختم کرتی ہے جنہیں کسی کو بھی کبھی منتخب نہیں کرنا چاہیے۔ ہر آپشن کو ایک لاگت-بمقابلہ-اثر ہوائی جہاز پر پلاٹ کرنا اور حد کھینچنا ایک پانچ منٹ کی مشق ہے جو معمول کے طور پر نصف مختصر فہرست کو ختم کر دیتی ہے۔ تدریجی موازنے ([ICERs](../بڑھوتی-لاگت-تاثیر-تناسب/)) پھر صرف *حد کے ساتھ ساتھ* حساب کیے جاتے ہیں، ہر آپشن اگلے سستے غیر-غالب کے خلاف — کبھی "کچھ نہ کرنا" کے خلاف نہیں جب بہتر درمیانی آپشنز موجود ہوں۔

## حساب

```
سخت غلبہ:      A، B پر غالب ہے اگر لاگت_A ≤ لاگت_B اور اثر_A ≥ اثر_B
                    (کم از کم ایک سخت عدم مساوات کے ساتھ)

توسیع شدہ غلبہ: B کو خارج کر دیا جاتا ہے اگر A اور C کا مرکب فی پاؤنڈ
                    زیادہ اثر حاصل کرتا ہے — پتہ چلتا ہے جب ICERs کم ہوتے ہیں جیسے آپ
                    حد کو اوپر جاتے ہیں۔ درست حد ICERs کو بڑھتا ہونا چاہیے۔
```

طریقہ کار: آپشنز کو اثر کے مطابق ترتیب دیں؛ سختی سے غالب کو ہٹا دیں؛ پڑوسیوں کے درمیان جوڑی دار ICERs کا حساب لگائیں؛ کوئی بھی آپشن ہٹا دیں جس کا ICER اگلے زیادہ موثر آپشن سے زیادہ ہو (توسیع شدہ غلبہ)؛ تکرار کریں جب تک ICERs یکطرفہ طور پر بڑھتے نہ جائیں۔

## حل شدہ مثال

چھوٹے ہوئے اپائنٹمنٹس کو کم کرنے کے چار آپشنز (اثر = بحال شدہ اپائنٹمنٹس/سال):

```
آپشن          لاگت/سال    بحال شدہ
کچھ نہیں کرنا  £0         0
SMS یاد دہانیاں   £20,000    2,000
فون کالز    £120,000   2,200
SMS + AI ٹریاج £90,000    3,500
```

فون کالز SMS + AI ٹریاج کی طرف سے **سختی سے غالب** ہیں (زیادہ لاگت رکھتا ہے، کم بحال کرتا ہے)۔ حد: کچھ نہیں → SMS → SMS + AI۔

```
ICER(SMS بمقابلہ کچھ نہیں)   = 20,000 / 2,000  = £10 فی بحال شدہ اپائنٹمنٹ
ICER(SMS+AI بمقابلہ SMS)    = (90,000 − 20,000) / (3,500 − 2,000) = £46.67 فی اپائنٹمنٹ
```

بڑھتے ICERs → درست حد۔ فی بحال شدہ ہسپتال اپائنٹمنٹ ~£160 بچت پر ([حاضر نہ ہونے کی شرح](../حاضر-نہ-ہونے-کی-شرح/) دیکھیں)، دونوں حد کے قدم اٹھانے کے قابل ہیں؛ فون-بینک تجویز کو کبھی کمیٹی تک نہیں پہنچنا چاہیے۔

## سافٹ ویئر انجینئرنگ سے تعلق

کسی بھی ٹولنگ فیصلے کے لیے ایک ہی چارٹ بنائیں: ایک محور پر فی سال لاگت، دوسرے پر ناپا گیا نتیجہ (بچائے گئے گھنٹے، اجتناب شدہ واقعات، فعال کردہ تعیناتیاں)۔ حد سے اوپر-اور-بائیں پوائنٹس کو کوئی بجٹ کے بارے میں بحث کرنے سے پہلے ہی ختم کر دیا جاتا ہے۔ یہ وینڈر انتخاب کو فیچر-چیک لسٹ کی بحثوں سے "آپ غالب ہیں؛ میٹنگ ختم ہو گئی" میں دوبارہ تشکیل دیتا ہے۔ یہ ایک معمولی فائدے کے لیے سب سے مہنگا آپشن خریدنے کے عام انٹرپرائز پیٹرن کو بھی بے نقاب کرتا ہے — قانونی صرف اگر فی تدریجی یونٹ تدریجی قیمت وہ ہو جو تنظیم جانتے بوجھتے ادا کرے۔

## نقصانات

- **ہر چیز کا بنیادی خط سے موازنہ کرنا** حد پر اگلے آپشن کی بجائے — یہ سستے قریبی مساوی کو چھپا کر مہنگے آپشنز کی چاپلوسی کرتا ہے۔
- **واحد-جہتی اثر اسکورز** جو اہم چیز چھپاتے ہیں؛ اگر دو نتائج شمار ہوتے ہیں، انہیں یا تو قابل دفاع طریقے سے یکجا کریں ([لاگت-افادیت تجزیہ](../لاگت-افادیت-تجزیہ/) دیکھیں) یا دو حدیں دکھائیں۔
- **غیر یقینی صورتحال کو بھولنا**: حد کے قریب آپشنز [حساسیت تجزیہ](../حساسیت-تجزیہ/) کے تحت جگہ بدل سکتے ہیں۔
