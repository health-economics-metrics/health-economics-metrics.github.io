# 技術的負債

技術的負債とは、コードベースにおける過去の便宜的な意思決定の暗黙の将来費用のことです:負っている修復作業(**元本**)と、デリバリーに及ぼし続ける負担(**利子**)です。SQALEのような定量化手法は、それを比喩から値付けされた負債へと変えます。

## なぜ重要か

定量化されなければ、技術的負債は愚痴です;定量化されれば、それはビジネスケースです。業界の基準値(CAST Appmarq、1,400アプリ/5億5,000万行):歴史的に、コード1行あたり約**3.61ドルの技術的負債の元本**であり、典型的なコードベースは再構築費用の15〜20%の負債比率を抱えています。これは、一般的に使われる健全性の基準である5%以下(SonarQubeの「A」グレード)と比較されます。医療経済学の枠組みはぴったり当てはまります:負債は*慢性疾患*です — 未治療のまま放置すると進行し、その「利子」は遅いデリバリーと高い欠陥率として複利で増え、修復は、予防が治療と競合するのとまったく同じように、機能開発と容量を奪い合います。

## 数式

```
SQALEの元本 = Σ 違反にわたって(修復時間) × 開発者の費用率
技術的負債比率(TDR) = 修復費用 / 再開発費用 × 100
                    (SonarQubeのグレード:A≤5%、B≤10%、C≤20%、D≤50%)

利子(返済を正当化する数値):
  年間利子 = Δデリバリー速度 × 速度単位あたりの価値
           + Δ欠陥率 × 欠陥1件あたりの費用
返済のケース = PV(評価期間にわたって回避された利子) − 修復費用
              (割引される — 割引と時間選好を参照)
```

元本は負債を述べます;**利子**が投資のケースを作ります。£40,000/年の利子を回避するために£500,000の元本を支払うのは悪い取引です;£400,000/年を回避するなら優れた取引です。

## 計算例

40万行の臨床記録統合レイヤー:SQALEの元本3,800時間×£75 = **£285,000**;TDR≈12%(グレードC)。測定された利子:このレイヤーに触れるチームは、資産全体の基準値と比較してサイクルタイムが40%長く、変更失敗率が2倍です。このレイヤーは年間6,000開発者時間を消費します:

```
利子 ≈ 6,000 × 0.40 × £75      = 年間£180,000(速度の負担)
     + 12件の追加の失敗 × £8,000 = 年間£96,000(手戻り/インシデント)
     ≈ 年間£276,000

ホットスポットを狙って元本の最悪の30%(£85,000)を修復する → モデル化された
利子削減60%:年間約£166,000を節約。回収期間≈6か月。
```

ホットスポットを狙うことが重要です:負債の利子は、変更頻度×負債密度が最大になる場所に集中します — めったに触れられない負債を修復しても、決して進行しなかったであろう状態を治療するのと同じように、何も得られません([予防の経済学](../予防の経済学/)を参照)。

## ソフトウェア工学との関連

技術的負債の議論を強化する医療経済学からの輸入品:資産を**負担一覧**([DALY](../障害調整生存年/)スタイル — 失われた健全なエンジニアリング年はどこにあるか?)として表現すること;返済を進行の数学で正直に正当化すること(通常は費用節約ではなく費用効果的);最悪のシステムの修復を[重症度不足分](../qaly不足分と重症度修正因子/)で重み付けすること;そして、大きな修復提案を、[回避された下流の費用](../回避された下流の費用/)のルール(確率で重み付けされ、割引され、一度だけ数えられる)に耐えられる相殺分析とともに提出すること。

## 落とし穴

- **元本のみの報告**:利子の推定なしの大きく恐ろしい数字は、何も正当化しません。
- **文字通りに受け取られるツール生成の負債の数値**:SQALEはルール違反を数えます;それはアーキテクチャ上の負債(高価な種類)を見逃し、些細なことを数えます。
- **負債ゼロのユートピア主義**:最適な負債水準はゼロではありません — 負債はレバレッジです;問題は利率です。
- **「書き直せばすべて回避できる」**:書き直しの提案は、同じ相殺のルール — 反実仮想の費用、確率、割引 — をクリアしなければなりません。
